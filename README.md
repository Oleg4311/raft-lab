# raft-lab

[![CI](https://github.com/Oleg4311/raft-lab/actions/workflows/ci.yml/badge.svg)](https://github.com/Oleg4311/raft-lab/actions/workflows/ci.yml)
[Релизы](https://github.com/Oleg4311/raft-lab/releases)

**Raft на C# (.NET 9) и симулятор, который пытается его сломать.** Алгоритм консенсуса написан как чистый конечный автомат (время и сообщения приходят снаружи), поэтому симулятор может прогонять кластер с потерей, дублированием и задержкой сообщений, разделением сети и падениями узлов, воспроизводить любой прогон по зерну и на каждом шаге проверять свойства безопасности из статьи. Отдельно проверяется **линеаризуемость** того, что видят клиенты. Чтобы доказать, что проверки не молчат, в код встроены шесть типичных ошибок реализации, и каждая ловится.

**Смотреть:** https://oleg4311.github.io/raft-lab/ (выборы, падение лидера, разделение сети и все шесть пойманных ошибок, по тикам) · [English](#english)

## Что внутри

| Часть | Что делает |
|---|---|
| `RaftLab.Core` | Узел Raft: выборы с рандомизированными тайм-аутами, репликация журнала, быстрый откат `nextIndex` по подсказке о конфликте, пустая запись нового лидера, коммит только записей текущего терма, автомат «ключ-значение» с таблицей сессий («ровно одно применение» при повторах клиента) |
| `RaftLab.Sim` | Дискретное время, сеть (задержки, потери, дубли, разделения), падения и перезапуски с сохранением терма, голоса и журнала, клиенты с повторами, проверки безопасности, проверка линеаризуемости, запись трасс |
| `raftlab` (CLI) | `fuzz` перебирает зёрна, `run` даёт подробный отчёт одного прогона, `traces` пишет сценарии для просмотрщика, `bugs` перечисляет встроенные ошибки |
| `web/` | Просмотрщик записей: узлы, летящие сообщения, журналы, таймлайн. Читает записи, полученные запуском симулятора |

## Что проверяется

Безопасность (после каждого шага, рис. 3 статьи): **Election Safety** (не больше одного лидера в терме), **Leader Append-Only**, **Log Matching**, **Leader Completeness**, **State Machine Safety**, плюс совпадение закоммиченных префиксов. После починки сети проверяется **живость**: есть лидер, узлы сошлись, у клиентов нет зависших операций. Наконец, вся история клиентов проверяется на **линеаризуемость** (поиск Wing и Gong с запоминанием состояний): чтение не возвращает устаревшее значение, повторы не применяются дважды, незавершённая операция могла и сработать, и нет. Для нарушения находится самый ранний момент, когда история уже не линеаризуема (бинарный поиск по префиксам).

## Пойманные ошибки

Каждая ошибка включается флагом и проверяется на закреплённом зерне; на том же зерне без ошибки всё чисто.

| Ошибка | Что ломается | Кто ловит |
|---|---|---|
| `CommitPreviousTermByCount` | запись прошлого терма коммитится по числу копий (рис. 8 статьи) | Leader Completeness |
| `NoUpToDateCheck` | голос отдаётся без проверки свежести журнала кандидата | Leader Completeness |
| `VoteNotPersisted` | голос не сохраняется на диск: после перезапуска узел голосует повторно в том же терме | Election Safety |
| `TruncateAlways` | любой `AppendEntries` с записями обрезает хвост, даже совпадающий (запоздавший дубль стирает закоммиченное) | Committed Prefix |
| `LocalReads` | лидер читает из своего состояния без подтверждения лидерства (устаревшее чтение в меньшинстве) | линеаризуемость |
| `NoDedup` | повтор команды применяется второй раз | линеаризуемость |

`CommitPreviousTermByCount` и `VoteNotPersisted` проявляются редко и требуют жёстких параметров (частые сбои, малые тайм-ауты, батч из одной записи): в таблице тестов закреплены именно такие прогоны.

## Что проверено

- **Корректная реализация.** 4000 случайных прогонов (8 млн тиков, около 480 тысяч операций, около 17 тысяч выборов лидера) без нарушений; 800 прогонов в жёстком режиме (потери 5%, сбои в 8% тиков, тайм-ауты 8–12, батч 1); кластеры из 1, 3 и 7 узлов. CI повторяет перебор на каждой правке.
- **72 теста xUnit.** Правила Raft по рис. 2 по пунктам (голосование, откат, конфликты, коммит), автомат, проверка линеаризуемости (ручные истории, 300 историй из настоящего последовательного выполнения всегда принимаются, подмена результата ловится), сами проверки безопасности на подстроенных нарушениях, шесть ошибок на закреплённых зёрнах.
- **Мутации самого Raft.** Вручную ломались 8 мест ядра (большинство минус один, нестрогая свежесть журнала, голос без сохранения, конфликтный хвост не удаляется, нет шага вниз при большем терме, нет пустой записи лидера, коммит выше присланного, и др.): тесты падают каждый раз.
- **Воспроизводимость между ОС.** Свой генератор (SplitMix64, проверен по опубликованным значениям) вместо `System.Random`: отпечатки прогонов закреплены тестами и должны совпасть на Windows и в Linux-CI. Записи сценариев в репозитории сверяются побайтно с пересчитанными.
- **Просмотрщик:** 10 сценариев Playwright на десктопе и телефоне (воспроизведение, разделение сети показывает двух «лидеров», нарушение в записях ошибок, целостность записей, axe в светлой и тёмной теме, прокрутка).

Находки по ходу работы: критерий живости проверялся ровно на последнем тике и ложно срабатывал на выборах, идущих в этот момент (добавлен льготный период); симулятор терял ответ клиента в кластере из одного узла (запись применялась раньше, чем регистрировалось ожидание); клиент симулятора после отказа «я не лидер» ждал полный тайм-аут (CI поймал зависшую операцию на одном зерне из 400 в кластере из 7 узлов, исправлено); `TruncateAlways` порождал бесконечные штормы отказов, из-за чего в записях пришлось ограничить число сообщений на тик.

## Честные ограничения

- **Нет сжатия журнала (снимков) и смены состава кластера.** Журнал растёт без границ, состав пяти узлов фиксирован.
- **Нет Pre-Vote и CheckQuorum.** Узел, долго сидевший в меньшинстве, при возвращении с большим термом сбивает лидера: это известная особенность базового Raft, она видна в жёстких прогонах как лишние выборы.
- **Модель диска упрощена.** Запись терма, голоса и журнала считается мгновенной и надёжной (перезапуск сохраняет всё, падение «посередине» записи не моделируется).
- **Случайный перебор, а не доказательство.** Нет полного обхода состояний (как в TLC для TLA+): отсутствие нарушений на тысячах прогонов повышает уверенность, но ничего не доказывает.
- **Линеаризуемость проверяется для регистра с `Put`, `Get`, `Cas`**, до 62 операций на ключ в прогоне; сложность поиска в худшем случае экспоненциальна, на этих размерах она не мешает.
- **Сеть и часы условные.** Это не настоящая сеть и не настоящее время: сообщения доставляются по тикам. Проект не проверялся на реальных машинах.
- **Просмотрщик воспроизводит записи, а не гоняет симулятор в браузере.** Новый сценарий создаётся командой `raftlab traces` и коммитится.

## Использование

Скачайте автономный файл для своей системы со страницы [Releases](https://github.com/Oleg4311/raft-lab/releases) (ставить .NET не нужно; контрольные суммы в `SHA256SUMS`, происхождение: `gh attestation verify <файл> --repo Oleg4311/raft-lab`) или запустите из исходников (нужен .NET 9):

```
dotnet run -c Release --project src/RaftLab.Cli -- fuzz --from 1 --to 1000          # корректная реализация: ожидается «нарушений в 0»
dotnet run -c Release --project src/RaftLab.Cli -- fuzz --bug TruncateAlways --stop-first --chaos 400 --settle 700
dotnet run -c Release --project src/RaftLab.Cli -- run --seed 455 --bug LocalReads --chaos 400 --settle 700 --trace /tmp/t.json
dotnet run -c Release --project src/RaftLab.Cli -- traces --out web/traces         # пересоздать записи для просмотрщика
```

Параметры `fuzz` и `run`: `--nodes`, `--chaos`, `--settle`, `--fault` (доля тиков со сбоем), `--drop` (доля потерянных сообщений), `--batch`, `--etmin`, `--etmax`.

## Разработка

```
dotnet build -c Release
dotnet test -c Release                 # 72 теста
npm install && npx playwright install chromium
npm run e2e                            # просмотрщик (поднимает локальный сервер сам)
```

Если на машине настроен прокси, для e2e добавьте `NO_PROXY=127.0.0.1,localhost`. Лицензия: MIT. Сделано с помощью Claude.

## English

**raft-lab** is a Raft implementation in C# (.NET 9) built as a pure state machine, plus a deterministic cluster simulator with message loss, duplication and delay, network partitions and crash/restart. Every step checks Raft's safety properties (Election Safety, Leader Append-Only, Log Matching, Leader Completeness, State Machine Safety), and the client history is checked for **linearizability** (Wing & Gong search with state memoization, finding the earliest violating moment). Six classic implementation bugs are built in and each one is caught: committing old-term entries by counting (paper's Figure 8), voting without the up-to-date check, a vote that is not persisted, over-eager log truncation, leader-local reads, and a missing client-request dedup.

Verified: 4000 random runs of the correct implementation with no violations (plus a harsh network mode and 1/3/7-node clusters), 72 xUnit tests, 8 manual mutations of the core all caught, bit-for-bit cross-OS reproducibility (own SplitMix64 PRNG; run digests pinned and compared on Windows and Linux CI), and a static viewer replaying simulator traces. Honest limits: no snapshots or membership changes, no Pre-Vote/CheckQuorum, simplified disk model, random search rather than model checking, replayed traces rather than a live simulator in the browser. MIT licensed. Built with Claude.
